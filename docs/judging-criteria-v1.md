# 판정 기준 v1 — 제출 한 건을 판정하는 순서와 조건

기준: [기획서 v3.2](<../AI 스케치 게임 서비스 기획서 v3.2.md>) §7·§8·§10, [API 계약](api-contract-v1.md), [카테고리 정리 v1.1](catalog-curation-v1.md), [모델 구조](model-architecture-v1.md), [점수 계산 규칙 v1](scoring-v1.md). 작성일: 2026-09-25. 상태: 초안.

여러 문서에 나뉘어 있던 판정 규칙을 제출 한 건이 거치는 순서대로 모은 문서다. 세부 필드·오류 코드·중복 처리의 기준은 여전히 API 계약이다. 이 문서는 판정 순서와 조건을 정리할 뿐 계약을 바꾸지 않는다.

**인식 임계값과 성공 임계값은 아직 없다.** 인식 모델과 보정용 검증 그림이 있어야 정할 수 있다(4절). 이 문서의 기호 τ는 정해지지 않은 값을 뜻한다.

## 1. 판정 순서

| 단계 | 하는 일 | 결과 |
|---|---|---|
| 0. 요청 검사 | 세션·소유권·문제·릴리스 버전을 확인한다. Top-3 형식도 확인한다(정확히 3개, 서로 다른 후보 ID, 0~1의 유한한 p, p 내림차순, p 합 ≤ 1 + 1e-6). | 어긋나면 판정하지 않고 4xx 오류. 시도로 세지 않는다. |
| 1. 중복 확인 | 요청 지문과 그림 키로 이미 확정된 결과가 있는지 찾는다. | 있으면 기존 결과를 그대로 반환. 재계산하지 않고 횟수도 늘리지 않는다. |
| 2. 보류 검사 | 점수를 낼 수 없거나 믿기 어려운 인식을 걸러 낸다(2절). | `deferred` + 사유. 점수·시도 번호 없음. |
| 3. 점수 계산 | [점수 계산 규칙 v1](scoring-v1.md)로 혼합 점수와 화면 점수를 만든다. | 화면 점수와 문자열(예: `38.72`) |
| 4. 성공 판정 | 점수와 별개로 Top-1과 확신도로 판정한다(3절). | `solved` 또는 `recognized` |
| 5. 확정·기록 | 시도 번호·최고 점수·성공 상태를 한 트랜잭션으로 확정하고 계산 내역을 저장한다. | 응답 반환 |

앞 단계가 끝나야 다음 단계로 간다. 보류된 제출은 점수 계산을 하지 않는다. 성공 여부는 점수 크기에서 추정하지 않는다.

### 모델 출력에서 Top-3까지 (브라우저)

1. 345개 logits 전체에 `softmax(logits / T)`를 한 번 적용한다. T는 보정값이며, 보정 전에는 1이다.
2. [카테고리 정리 v1.1](catalog-curation-v1.md)에 따라 원본 확률을 대표 ID별로 **합산**해 335개 인식 후보를 만든다. 합산 후 재정규화하지 않는다.
3. 미지원 후보 `bird`도 자기 ID와 확률을 그대로 가진다.
4. p 내림차순으로 Top-3를 뽑는다. 같은 p이면 후보에 속한 원본 `class_index`의 최솟값 순서를 따른다.

아래 판정의 p는 전부 이 **원래 p**(전체 확률 질량을 보존한 합산 값)다. 후보 비중 `q = p / Σ(Top-3 p)`는 3단계의 점수 혼합에만 쓴다. 보류·성공 판정에는 쓰지 않는다.

## 2. 판정 보류 (`deferred`)

아래 순서로 검사하고, 처음 걸린 사유 하나를 기록한다.

| 사유 코드 | 조건 | 비고 |
|---|---|---|
| `low_confidence` | Top-3의 p 합이 0 | 혼합 계산 자체가 불가능하다 |
| `unsupported_candidate` | Top-3에 점수 미지원 후보(현재 `bird`)가 하나라도 있음 | 미지원 후보를 빼고 나머지만으로 점수를 내지 않는다 |
| `low_confidence` | `p1 < τ_인식` | 임계값 미정. p1은 Top-1의 원래 p |
| `low_confidence` (후보) | `Σ(Top-3 p) < τ_합` | 쓸지 여부부터 평가 후 결정 |
| `insufficient_attributes` | 비교할 수 있는 축이 기준보다 적음 | 점수 v1에서는 연상·분류·형태 축이 모든 점수 지원 카테고리에 있어 발생하지 않는다. 속성을 추가·수정할 때를 위해 남겨 둔다. |

- 보류는 서버 로그에 남기지만 **게임 시도 횟수에 넣지 않는다.** 점수를 0으로 만들지 않는다.
- 화면 안내 초안: "아직 어떤 그림인지 알아보기 어려워요. 특징을 조금 더 그려주세요."
- 미지원 후보 보류도 같은 문구를 쓴다. 어떤 후보 때문에 보류됐는지는 화면에 밝히지 않는다.
- 빈 캔버스는 브라우저에서 제출 자체를 막는다. 서버까지 오지 않는다.

## 3. 성공 (`solved`)

**성공 조건: 아래 두 가지를 모두 만족해야 한다.**

1. Top-1 후보 ID(매핑 후 대표 ID)가 오늘의 정답과 같다.
2. 그 후보의 원래 p가 `τ_성공` 이상이다. 임계값은 미정이다.

필요하면 `p1 − p2 ≥ δ`(1위와 2위 차이)를 세 번째 조건으로 검토한다. 현재는 쓰지 않는다.

**성공이 아닌 경우**

- 정답이 Top-2나 Top-3에만 있다.
- 혼합 점수나 관계 점수가 높다(예: 정답이 사자인데 호랑이로 인식되어 점수가 높은 경우).
- 속성 태그가 정답과 모두 같은 다른 카테고리로 인식됐다. 단, 대표로 통합된 원본은 확률이 정답 후보로 합쳐지므로 여기에 해당하지 않는다(예: 정답이 버스면 통학버스 그림은 성공할 수 있다).
- q(Top-3 안에서 다시 나눈 비중)가 높다.

**정답 인정 범위 (카테고리 정리 v1.1)**

- 통합된 원본은 대표 ID로 확률이 합쳐지므로, 그 원본을 그려도 대표 정답으로 성공할 수 있다.

| 대표 정답 | 함께 인정되는 원본 | 성격 |
|---|---|---|
| 컵 | 머그잔, 커피잔 | 하위 종류 |
| 버스 | 통학버스 | 하위 종류 |
| 트럭 | 픽업트럭 | 하위 종류 |
| 케이크 | 생일 케이크 | 하위 종류 |
| 시계 | 알람시계 | 하위 종류 |
| 수염 | 턱수염 | 하위 종류 |
| 발 | 발가락 | 부분을 전체로 인정 (초안) |
| 팔 | 팔꿈치 | 부분을 전체로 인정 (초안) |
| 다리 | 무릎 | 부분을 전체로 인정 (초안) |

- 통합 보류 6쌍은 서로의 정답으로 인정하지 않는다. 첼로–바이올린, 블랙베리–블루베리, 크레용–연필, 여권–책, 식기세척기–세탁기, 허리케인–토네이도다.
- `bird`는 정답이 될 수 없다. 개별 새 정답은 Top-3에 `bird`가 섞이면 보류된다.
- 부분을 전체로 인정하는 규칙은 출시 전 플레이 테스트로 유지 여부를 정한다.

**성공한 뒤**

- 응답에만 정답(`answer`)이 들어간다. 성공 전 응답에는 정답 필드 자체가 없다.
- 같은 문제의 새 그림 제출은 `409 GAME_ALREADY_SOLVED`로 거부한다. 이미 처리한 요청의 조회는 허용한다.

## 4. 임계값을 정하는 방법

| 값 | 의미 | 정하는 자료와 기준 | 현재 |
|---|---|---|---|
| `T` | 전체 logits 온도 보정 | 보정용 분할에서 NLL 최소화 | 미정(보정 전 1) |
| `τ_인식` | 이보다 낮은 p1은 보류 | 보류율과 "보류하지 않은 제출 중 오인식률"의 절충. 빈 그림·점·직선·낙서·지원 밖 대상 포함 | 미정 |
| `τ_합` | Top-3 합 최소값 | 위와 같은 자료로 필요성부터 평가 | 사용 여부 미정 |
| `τ_성공` | 정답 Top-1 성공 확신도 | **잘못된 성공률**(정답이 아닌 검수 그림 중 성공 처리 비율, 분모 명시)을 목표 이하로 | 미정 |
| `δ` | 1·2위 차이 | 비슷한 카테고리 사이 잘못된 성공이 문제될 때만 | 사용 안 함 |

**평가 규칙**

- **자료 분리**: 모델 선택용과 보정·임계값용 validation을 나누고, 최종 테스트 분할로 임계값을 고르지 않는다.
- **매핑 기준 평가**: 매핑 적용 후(335개 후보) 기준으로 평가하고, 원본 345개 기준 결과도 따로 남긴다. 합산이 확신도 분포를 바꾸기 때문이다.
- **검증 그림 구성**: 실제 그림판으로 그린 그림을 포함한다. 혼동 쌍, 통합 원본, 부분 그림을 넣는다(예: 발 정답에 발가락 그림).
- **버전 고정**: 임계값을 바꾸면 인식 기준·성공 조건 버전을 올린다. 진행 중인 문제는 발행된 버전을 유지한다.

모델이 준비되기 전 개발·테스트에서는 [합성 제출 사례](../contracts/fixtures/submission-cases.json)처럼 결과를 직접 지정하는 가짜 판정기를 쓴다. 이때의 값은 운영 임계값이 아니다.

## 5. 기록하는 계산 내역

판정 결과를 재현할 수 있도록 제출마다 아래를 저장한다(기획서 §11.4, DB `submission_score_details`).

- **인식**: Top-3 후보 ID와 원래 p, Top-3 합, 후보 비중 q
- **판정**: 상태(`recognized`/`deferred`/`solved`)와 보류 사유
- **점수 내역**:
  - 후보별 축 점수(분류·형태·기능·연상, 빠진 축은 null)와 관계 점수 R
  - 후보별 관계 순위
  - 혼합 점수, 화면 점수와 문자열
- **버전**: 모델, 전처리, 카테고리(`catalog-curation-v1.1`), 출력 보정, 점수 체계(`scoring-v1`), 인식 기준, 성공 조건
- **적용한 임계값 값 자체**

`backend/app/modules/judging/scorer.py`의 `mix_top3` 결과(`MixResult`)가 후보별 축 점수·R·순위·q를 담는다. 보류·성공 판정과 기록은 아직 작성하지 않은 `judge.py`와 `submissions/service.py`가 맡는다.

## 6. 예시

점수는 점수표 v1의 실제 값이다. τ는 정해지지 않았으므로 조건식으로만 적는다.

| 정답 | 인식 결과 (원래 p) | 판정 |
|---|---|---|
| 기린 | 말 0.50 · 얼룩말 0.20 · 소 0.10 | `p1=0.50 ≥ τ_인식`이면 `recognized` **76.56**. Top-1이 기린이 아니므로 성공 아님 |
| 기린 | 기린 0.55 · 말 0.20 · 낙타 0.10 | 점수 **90.21**. `0.55 ≥ τ_성공`이면 `solved`, 아니면 `recognized` |
| 기린 | 자동차 0.60 · 버스 0.20 · 트럭 0.10 | `recognized` **7.28** |
| 기린 | 새 0.60 · 올빼미 0.20 · 오리 0.10 | `deferred` / `unsupported_candidate`. 점수·시도 없음 |
| 컵 | 원본 머그잔 0.40 · 컵 0.15 · 커피잔 0.10 | 브라우저가 합산해 Top-1이 컵 0.65. `0.65 ≥ τ_성공`이면 `solved` |
| 누구든 | Top-3 p가 모두 0 | `deferred` / `low_confidence` |

## 7. 아직 정하지 않은 것

- τ_인식, τ_합, τ_성공, δ의 값과 사용 여부 (모델 필요)
- 서버 재추론 여부. 초기 MVP는 브라우저 결과로 판정하며, 이는 그림을 서버가 검증했다는 뜻이 아니다.
- 화면에 AI 예측 단어·관계 순위를 보여 줄지, 정답별 기준값(1위·10위 점수)이나 온도 표현을 보여 줄지
- 부분을 전체로 인정하는 규칙(발가락→발 등)의 유지 여부
